# Критические

## V2-CRIT-01 — Гонка двух писателей в pipe → неограниченная запись за пределы буфера ядра

**Файл:** `kernel/vfs/pipe.c` (`pipe_write_vop_write`, строки 142–214; ключевые — 163–206)

Копирование данных выполняется 256-байтовыми порциями, и **спин-лок отпускается на время каждой `copyin`**. В этом окне второй писатель (два процесса после `fork`, унаследовавшие write-конец, или два потока) продвигает `head`/`count`:

```c
// pipe.c:163-166 — оба писателя видят один и тот же space
usize space = PIPE_BUF_SIZE - pipe->count;
if (space > 0) {
    usize to_write = uio->uio_resid;
    if (to_write > space) to_write = space;
    ...
// pipe.c:205-206 — оба выполняют после своих copyin
pipe->head = (pipe->head + to_write) % PIPE_BUF_SIZE;
pipe->count += to_write;              // ← count учитан ДВАЖДЫ
```

Результат каскада:

1. `count` становится **больше** `PIPE_BUF_SIZE` (65536).
2. Следующий вызов `pipe_write`: `space = PIPE_BUF_SIZE - pipe->count` — **underflow `usize`** → гигантское «свободное место».
3. `to_write = uio->uio_resid` — уже **не ограничено ничем** (длина пользовательского буфера).
4. Цикл `memcpy(&pipe->buf[copied], tmp, step)` пишет на `copied` от 0 до `second_chunk` (десятки МБ) — **запись за пределами `buf[65536]` поверх полей `chimera_pipe_t` и соседних структур статического массива `s_pipes[32]`**.

**Эксплуатация:** тривиальна и реалистична — обычный shell-пайплайн `a | b`, где оба писателя в него пишут; уже одна гонка ломает `count`, вторая даёт управляемую по длине и содержимому запись в kernel `.data`.

**Фикс:** копировать во временный буфер **под локом** одним куском (или держать лок на всё копирование с заблокированными прерываниями — объёмы малы); ввести инвариант `count <= PIPE_BUF_SIZE` с паникой/логом; после повторного взятия лока **пересчитывать** `head/space`, а не доверять старым значениям. Аналогичная правка нужна в `pipe_read_vop_read` (строки 48–113: двойное чтение тех же байтов двумя читателями).

## V2-CRIT-02 — Паника ядра из ring 3: чтение пользовательского RSP в обработчике #PF

**Файл:** `kernel/arch/x86_64/idt.c:261-268`

```c
if (frame->rsp > 0x1000 && frame->rsp < 0x800000000000ULL) {
    u64 *sp = (u64 *)frame->rsp;
    kprintf("        stack: [rsp]=0x%llx ... [rsp+32]=0x%llx\n",
            sp[0], sp[1], sp[2], sp[3], sp[4]);
```

Проверяется только **диапазон** указателя, но не то, что страницы по этому адресу **замаплены**. Пользователь кладёт в RSP корректный по величине, но незамапленный адрес (например, `0x700000000000`) и провоцирует любой fault (обращение по NULL) — `sp[0]` даёт вложенный #PF **в kernel mode** → `chimera_panic("Page Fault in Kernel Mode…")`.

**Эксплуатация:** 5 строк ассемблера из usermode = гарантированная паника всего ядра. Классический тривиальный DoS.

**Фикс:** не дампить пользовательский стек вообще, либо читать его через `copyin`/`pmap_extract` с проверкой каждого квадрослова. Плюс общий принцип: **ядро никогда не разыменовывает пользовательские указатели напрямую**.

## V2-CRIT-03 — Обработчик COW-фолтов полностью без синхронизации → UAF физических страниц

**Файл:** `kernel/arch/x86_64/idt.c:198-230`

COW-путь `pmap_clone_user_space()` (том 1 не покрывал его обработчик фолта) читает PTE, проверяет `pmm_get_refcount`, аллоцирует страницу, копирует 4 КБ, освобождает старую и пишет PTE — **всё это без `s_pmap_lock`**:

```c
if (refcount > 1) {
    u64 new_phys = pmm_alloc_page();
    ...
    memcpy((void*)(new_phys + g_hhdm_base), (void*)(old_phys + g_hhdm_base), 4096);
    ...
    pmm_release_page(old_phys);            // ← оба потока/ядра сделают это
    *pte_ptr = (new_phys & ~0xFFFULL) | (*pte_ptr & 0xFFFULL) | PAGE_WRITE;
```

Два потока (в parent и child после fork) одновременно фолтят ту же COW-страницу: оба видят `refcount == 2`, оба копируют, оба вызывают `pmm_release_page(old_phys)` → **рефкаунт падает до 0 при живом маппинге** → PMM отдаёт страницу под новые аллокации → две разные задачи пишут в одну физическую страницу. Это межпроцессная порча памяти с полной управляемостью содержимого.

**Фикс:** весь COW-путь под `s_pmap_lock` (или хотя бы compare-and-swap на PTE + повторная проверка refcount после захвата лока); `invlpg` после обновления PTE уже есть — сохранить.

## V2-CRIT-04 — `sys_setuid` без проверки прав: модель привилегий декоративна

**Файл:** `kernel/bsd/syscall.c:2992-3000`

```c
static i64 sys_setuid(u64 uid, ...) {
    chimera_task_t *t = current_task();
    if (t && t->ta_proc) {
        t->ta_proc->p_uid = (chimera_uid_t)uid;
        // p_euid присваивается аналогично, без каких-либо проверок
```

Любой процесс вызывает `setuid(0)` и мгновенно становится root — парольная проверка в `su(1)`/`login(1)` живёт **только в userland** и ничего не значит. Усилители, найденные в этом же проходе:

- `/etc/master.passwd`: `root::0:0::...` — **пустой пароль root**;
- FAT32 не имеет прав — `/etc/master.passwd` перезаписываем любым процессом;
- `sys_kill` (syscall.c:2044-2060) убивает **любой** PID без проверки euid;
- `/dev/disk0` — raw-доступ к диску из userland без прав (V2-MED-01).

**Фикс:** в `sys_setuid` разрешать смену uid только на собственный uid/сохранённый suid, кроме случая `p_euid == 0`; то же для `setgid`. Это точечная правка, но она включает всю модель привилегий.

# Высокие

## V2-HIGH-01 — Гонка разрушения процесса на SMP: UAF таблиц страниц

`proc_mark_exited` (kernel/bsd/proc.c:215+) вызывает `pmap_destroy_user_space` (kernel/mm/pmap.c:240-291), освобождая pml4/PDPT/PD/PT и пользовательские страницы. Но `scheduler_remove_thread()` **не синхронизирован** с исполнением потока на другом CPU: поток, уже выбранный и запущенный на втором ядре, может вернуться в ring 3 через `iretq` с CR3, указывающим на **уже освобождённую таблицу страниц**. Мгновенный use-after-free всей иерархии трансляции.

**Фикс:** двухфазный teardown — сначала пометить потоки `HALTED` и дождаться (`th_running_cpu == -1`/барьер) фактического ухода с CPU, только потом `pmap_destroy_user_space`.

## V2-HIGH-02 — Нет TLB-shootdown при разрушении адресного пространства

`pmap_destroy_user_space` освобождает pml4 в PMM **без** `smp_tlb_shootdown()` (и даже без локальной перезагрузки CR3). Без PCID TLB-записи тегируются значением CR3: когда PMM переиспользует ту же физическую страницу под pml4 **нового** процесса, новый CR3 численно совпадает со старым — и на других CPU «оживают» призрачные TLB-записи умершего процесса. Готовый вектор утечки данных между процессами (и порчи, если страницы переиспользованы под ядро).

**Фикс:** в конце `pmap_destroy_user_space` — `smp_tlb_shootdown()`; при аллокации нового pml4 из PMM — полная инвалидация (у них общий helper уже есть).

## V2-HIGH-03 — Паника ядра при заполнении очереди планировщика (64 потока) + вечные зомби

`scheduler_add_thread` (`kernel/arch/x86_64/scheduler.c:119-125`):

```c
if (g_run_count >= SCHED_MAX_THREADS) {   // 64
    chimera_panic("scheduler_add_thread: run queue full ...");
```

Пулы процессов/задач тоже статичны по 64 (`proc.c:17-18`), а слоты возвращаются **только** в `proc_reap` (через `wait4`). Итог: 64 незариперенных зомби (или просто 64 живых процесса) — и следующий `fork`/`spawn` любой программы **валит ядро паникой**. Плюс утечка слотов навсегда, если родитель не вызвал wait.

**Фикс:** возвращать `EAGAIN` вместо паники; принудительный reap зомби (reaper-поток или reparenting на init); динамические пулы или завышенные лимиты с отказом, а не паникой.

## V2-HIGH-04 — Неограниченный рост пользовательского стека по требованию

`kernel/arch/x86_64/idt.c:232-247`: любой #PF в диапазоне `[0x00007FF000000000, 0x00007FFFFFFFFFFF]` аллоцирует и мапит новую RW-страницу — **без лимита RLIMIT_STACK и без верхнего предела**. Диапазон ~1 ТБ; каждое касание «украденной» адресной области съедает одну физическую страницу навсегда (эти страницы не регистрируются в vm_map → `munmap` их не возвращает, при exit освобождаются только страницы, достижимые из pml4 — они достижимы, но до этого момент может не дойти при DoS).

**Эксплуатация:** цикл `*(volatile char*)(0x7FF000000000 + i*4096) = 1;` исчерпывает всю физическую память; PMM начинает возвращать ошибку/`-1` — а большинство вызывающих кода (как в V2-CRIT-03) это не проверяет.

**Фикс:** жёсткий лимит размера стека (например, 8 МБ от stack top), проверка `sp - cr2 < limit`, отказ с SIGSEGV.

## V2-HIGH-05 — Глобальный `g_syscall_frame` без per-CPU изоляции → кража чужого syscall-фрейма

`kernel/bsd/syscall.c:3838` (`g_syscall_frame = frame;`) — **одна глобальная переменная на всё ядро**. На SMP CPU-0 и CPU-1, одновременно находящиеся в syscall, перезаписывают её. `sys_fork` (строка 883) читает её:

```c
syscall_user_frame_t *frame = (syscall_user_frame_t *)g_syscall_frame;
uptr child_rip = frame->rip;
uptr child_rsp = frame->rsp;
```

При гонке child получает **RIP/RSP/регистры чужого процесса** с другого CPU: дочерний процесс начинает исполняться по чужому адресу — утечка чужого кода/данных и исполнение в неправильном контексте.

**Фикс:** передавать frame параметром в `sys_fork` (он уже доступен в `syscall_dispatch`), либо per-CPU хранилище.

## V2-HIGH-06 — `sys_kill` без проверки прав + kill(0) затрагивает kernel proc

`kernel/bsd/syscall.c:2044-2060`: нет сравнения uid/euid цели и отправителя, нет запрета на pid 0 (`proc_find_by_pid(0)` возвращает `proc_kernel`). Любой процесс снимает launchd, любой пользователь убивает чужие сессии.

**Фикс:** проверка `target->p_euid == cur->p_euid || cur->p_euid == 0 || target == cur`, запрет pid 0/1 без привилегий.

## V2-HIGH-07 — Двойное наследование fd в fork → утечка refcount всех дескрипторов

`proc_create` уже копирует таблицу fd с `fp_retain` (proc.c), **а затем** `sys_fork` (syscall.c:842-851) копирует её **повторно**: `fp_retain(fp)` и запись поверх уже существующего указателя без `fp_release` старого. Итог: у каждого fd после fork refcount завышен на 1 → fileproc/сокеты/pipe никогда не освобождаются → на каждый fork утечка всех открытых дескрипторов (сокеты — вместе с mbuf-буферами).

**Фикс:** убрать дублирующий цикл из `sys_fork` (proc_create уже всё сделал).

## V2-HIGH-08 — Неинициализированный паддинг `chimera_event_t` → утечка стека ядра через /dev/kbd, /dev/mouse

`kernel/include/kernel/input.h:32-47`: структура 24 байта (type(4) + padding(4) + union(12-16) + хвостовой padding(4)). В `hid.cpp` (`push_key_event`) поля не-union части и паддинги **не обнуляются** — пользователь читает массив событий через `/dev/kbd`/`/dev/mouse` (devfs.c) и получает 4–8 байт **мусора со стека ядра** на каждое событие; очередь 1024 событий позволяет массовую утечку (указатели, остатки данных).

**Фикс:** `chimera_event_t ev = {};` (zero-init) перед заполнением.

# Средние

## V2-MED-01 — `/dev/disk0`: raw-доступ к диску без прав + LBA-усечение + RMW-гонка

`kernel/vfs/devfs.c` (`s_disk_ops`) открывает блочное устройство любому процессу: чтение/запись произвольных секторов = обход VFS целиком (перезапись ядра на диске, чтение любых файлов). В `kernel/drivers/ata.c:233-250`:

```c
if (lba + count > g_ata_drive.sector_count) return CHIMERA_ERR_OVERFLOW;
...
ata_write_single_sector_lba28((u32)(lba + i), ...);   // ← усечение до 32 бит
```

Граница проверяется в u64, но команда LBA28 получает `(u32)lba` — на дисках >128 ГиБ пишется **не тот сектор** (например, LBA 0x10000000 превращается в 0). `dev_disk_write` делает read-modify-write 512-байтового стека без лока → интерливинг двух писателей.

**Фикс:** права на устройство (root-only), LBA48-команды для больших LBA, лок на RMW.

## V2-MED-02 — `dev_serial_write`: пользовательский указатель напрямую в `serial_puts`

`kernel/vfs/devfs.c:170-172`:

```c
serial_puts((const char *)uio->uio_buf);   // без copyin!
```

`uio_resid` игнорируется: (а) невалидный указатель → kernel-mode #PF → паника (как V2-CRIT-02); (б) строка читается до первого NUL **за границей буфера** → утечка пользовательской памяти в serial-лог.

**Фикс:** `copyin` в стековый буфер длиной `uio_resid` + NUL-терминация.

## V2-MED-03 — Порядок инициализации зон: `zone_init()` затирает зоны vm_map/vm_object

`kernel/chimera_kernel_main.c:373-380`: сначала `vm_object_init()` и `vm_map_init()` (создают зоны №0–2 в `s_zone_table`), затем `zone_init()` делает `s_zone_table_count = 0` и создаёт kalloc-зоны **поверх** них. Хендлы `s_vm_obj_zone`/`s_vm_map_zone` теперь алиасят `kalloc.16/32/64` (элементы по 16/32/64 байта), а структуры больше. Сейчас API vm_map/vm_object фактически не вызывается (латентно), но первый же вызов `vm_map_create`/`vm_object_create` даст **запись за пределы элемента зоны** → порча кучи.

**Фикс:** убрать сброс счётчика из `zone_init()` (или инициализировать зоны до `vm_*_init`).

## V2-MED-04 — `kalloc`: целочисленное переполнение `size + sizeof(header)`; `kfree` без валидации

`kernel/mm/zone.c:166-235`:

- `size + sizeof(zone_header_t)` и `size + sizeof(large_header_t)` без проверки переполнения: `kalloc(0xFFFFFFFFFFFFFFF0)` → маленький аллок, затем `memset(ptr, 0, size)` **огромной длиной** → стирание памяти ядра. Любой syscall, передающий пользовательскую длину в kalloc (заголовки сообщений, буферы setsockopt и т.п.), превращается в write-примитив.
- `kfree` читает 16 байт **перед** указателем и верит `ZONE_MAGIC`/`LARGE_MAGIC` — свободный произвольный указатель = высвобождение случайной памяти; double-free не детектируется (нет poisoning).

**Фикс:** `if (size > SIZE_MAX - 64) return NULL;`, проверка выравнивания и диапазона ptr, poison-паттерн при `zfree`.

## V2-MED-05 — `vm_map_protect` игнорирует `vme_max_prot`

`kernel/mm/vm_map.c` (`vm_map_protect`): новая защита применяется к пересекающимся записям без маски `& ~vme_max_prot` — `mprotect` может **повысить** права (RO→RW, добавить X) сверх максимально допустимых для объекта (например, файл, замапленный read-only). Права файла/`max_protection` перестают быть границей.

**Фикс:** `new_prot &= entry->vme_max_prot;` (отказ, если после маскирования права «уехали» ниже текущих).

## V2-MED-06 — `vm_map_enter`: нет проверки пересечений и границ

`kernel/mm/vm_map.c` (`vm_map_enter`): при явно заданном адресе запись вставляется **без проверки пересечения** с существующими записями (двойной маппинг одного диапазона); `start + size` не проверяется на переполнение и против `vmm_max_offset` — записи могут «выезжать» за пользовательскую половину. `vm_map_remove` удаляет только **полностью попадающие** записи: частичный `munmap` середины региона оставляет entry, хотя PTE уже сняты (`pmap_unmap_user_range` вызывается на весь диапазон) → рассинхрон map/pmap; повторный мап той же области поверх «фантомной» записи даёт двойные записи и утечки.

**Фикс:** поиск пересечений при вставке; clip/trim частично пересекающихся записей при remove/protect (как в XNU `vm_map_clip_start/end`).

## V2-MED-07 — `vm_object_fault`: границы offset и write-фолт игнорируются, TOCTOU вставки

`kernel/mm/vm_object.c:154-195`: `(void)fault_type;` — write-фолт на COW-объекте не копирует страницу (COW на уровне объектов не работает); `offset` не проверяется против `vmo_size` — фолт за пределами объекта аллоцирует и добавляет страницу; вставка страницы в список происходит под локом, но **поиск** — без → гонка двух фолтов создаёт две страницы одного offset (одна теряется в списке).

*Сейчас вызовов нет (мёртвый код), но при включении demand paging это прямые баги.*

## V2-MED-08 — Единственный глобальный PTY: кейлоггинг и инъекция любым процессом

`kernel/vfs/pty.c:46` (`static pty_t g_pty0;`) — один PTY на всю систему, без владения/прав. Любой процесс открывает `/dev/ptmx` (или `/dev/pts/0`) и читает то, что печатает жертва в своём терминале (включая **пароли**), либо инъектирует ввод в чужую сессию.

**Фикс:** per-open аллокация PTY (пул с референсами), проверка владельца сессии на master-стороне.

## V2-MED-09 — Непрерываемые ожидания: неубиваемые процессы

`pipe_read/write` (pipe.c:48-113,150-214), PTY-чтения (pty.c), `mach_msg` receive (ipc_kmsg.c:428) крутятся в `wait_queue_sleep` **без проверки отложенных сигналов**. SIGKILL доставляется только на выходе из syscall — заблокированный в pipe-чтении процесс **нельзя убить никогда**. Вместе с лимитом 64 потока (V2-HIGH-03) — постоянная исчерпываемость планировщика.

**Фикс:** в циклах ожидания проверять `p_sigpending`/`th_state` и выходить с `EINTR`.

## V2-MED-10 — `vfs_normalize_path`: сегменты длиннее 63 байт молча выбрасываются

`kernel/vfs/vfs.c` (`vfs_normalize_path`, буферы `segs[16][64]`): сегмент 65+ байт **пропускается**, а не отклоняется. `open("/etc/<72 символа>/shadow")` превращается в `open("/etc/shadow")` — path confusion: обход префиксных проверок каталогов, обращение не к тому vnode.

**Фикс:** возвращать `ENAMETOOLONG` вместо пропуска сегмента.

## V2-MED-11 — Реестр VFS: удаление без tombstone + незащищённый счётчик

`kernel/vfs/vfs.c`: хеш-таблица с open addressing; `vfs_unregister` обнуляет слот **без tombstone** → обрыв цепочек проб → соседние файлы «исчезают», а последующий `vfs_register` вставляет в освободившийся слот **внутрь чужой цепочки** → одному пути соответствуют два vnode (подмена файла по имени). `s_rootfs_vnode_count++` в `vfs_register`/`ensure_parent_dirs` выполняется **без лока** (лок берётся позже) — гонка на SMP даёт одинаковые индексы/порчу.

**Фикс:** tombstone-слоты, вынести инкремент под `s_registry_lock`.

## V2-MED-12 — `sys_poll` молча опрашивает только первые 32 из 256 дескрипторов

`kernel/bsd/syscall.c:3284-3299`: `nfds` допустим до 256, но `struct chimera_pollfd fds[32]; count = min(nfds, 32)` — события на fd #33+ **никогда не возвращаются** и не помечаются. Приложения, опрашивающие много fd (демоны), теряют готовность → зависания и потеря данных.

**Фикс:** динамический буфер (kalloc) под все `nfds` с возвратом ошибки при нехватке памяти.

## V2-MED-13 — Сигнальная подсистема — заглушка: обработчики не вызываются, sigmask не работает

`kernel/bsd/proc.c` (`proc_deliver_signals`): при установленном `sigaction`-обработчике функция просто `return` — **ни сигнального фрейма, ни вызова обработчика, ни sigreturn**; `sa_mask`/`sa_flags` сохраняются, но ни на что не влияют; сигналы либо молча глотаются, либо убивают процесс. Пользовательские обработчики SIGSEGV/SIGCHLD и т.п. не работают в принципе. Зависимости таймингов (race с `p_lock` при copyin в `sys_sigaction`) — второстепенны.

**Фикс:** строить signal frame на пользовательском стеке (или выделенной altstack-странице) и переходить по `p_sigacts[sig]`.

## V2-MED-14 — fork: статический пул потоков без лока + повторное использование слота

`kernel/bsd/syscall.c:887-901`: `static chimera_thread_t s_fork_threads[64]` ищется свободный слот **без блокировки** — два CPU одновременно форкают → один и тот же слот → два процесса на одном `chimera_thread_t` (общий kernel-стек!) → порча стека/контекста. Слот считается свободным по `th_state == HALTED`, при этом закрученный в `while(1) scheduler_yield()` поток выхода (sys_exit_direct:150) всё ещё живёт на этом же стеке.

**Фикс:** лок на выбор слота; выделение стека из PMM и корректное завершение потока вместо вечного spin.

## V2-MED-15 — Утечка памяти на каждый exit/неудачный exec

- Kernel-стек потока (4 страницы, `thread_init_stack`, scheduler.c:26-50) **никогда не освобождается**;
- страницы пользователя освобождаются только при корректном проходе `pmap_destroy_user_space`, который недостижим, если слот задачи не вернулся в пул (нет wait4);
- `mach_loader.c`: при ошибке после частичного маппинга (E2BIG/ENOMEM на середине) уже замапленные сегменты и выделенные страницы стека не освобождаются — crafted Mach-O → гарантированная утечка на каждый вызов.

**Фикс:** освободить стек в teardown потока; rollback-метка в загрузчике.

## V2-MED-16 — `proc_fd_close_cloexec` держит `p_fdlock` (irqsave) при `fp_release`

`kernel/bsd/fileproc.c` (блок `proc_fd_close_cloexec`): закрытие дескрипторов выполняется **внутри** критической секции с выключенными прерываниями → `fp_release` → `soclose` (сетевой teardown, ожидания, kprintf) под локом. Потенциальный дедлок и секундные окна с погашенными IRQ на exec. Обычный `proc_fd_close` делает это правильно — после unlock.

**Фикс:** собрать список fd под локом, освобождать после.

## V2-MED-17 — Приоритетное голодание в планировщике + привязка потоков к CPU

`kernel/arch/x86_64/scheduler.c:180-194`: выбор строго по приоритету, без aging — поток с высоким приоритетом, крутящийся в usermode, **навсегда** вытесняет низкоприоритетные (на одноядерной конфигурации — заморозка системы). `th_running_cpu` после первого запуска закрепляет поток за одним CPU — балансировки нет.

**Фикс:** decay/aging приоритетов со временем; сброс `th_running_cpu` при усыплении.

# Низкие

## V2-LOW-01 — `ioctl(FBIOPAN_DISPLAY)` не валидирует `pan.yoffset`

`kernel/vfs/devfs.c`: значение из usermode пишется в регистры Bochs VBE без проверки против высоты фреймбуфера → скан-аут за пределы VRAM (на экран пролезает соседняя видеопамять — утечка ~КБ, косметика).

## V2-LOW-02 — Таймерное прерывание опрашивает HID и ATA держит IRQ выключенными до секунд

`idt.c:164-174` (`chimerakit_hid_poll()` в каждом тике) и `ata.c:46-55` (PIO-ожидание до 1 млн чтений порта при выключенных прерываниях) — джиттер/потеря тиков, DoS-усилитель по таймингу.

## V2-LOW-03 — 8.3-фолбэк и case-insensitive сравнение путей

`vfs.c` (`vfs_path_to_83`, `k_strncasecmp`): длинные имена молча усекаются до 8.3 — запрос `/etc/verylongname` может разрешиться в другой зарегистрированный файл `/etc/verylon`.

## V2-LOW-04 — `su(1)`/`login(1)`: нет задержки при неверном пароле, `strcmp` не constant-time

`usr/bin/su.c`, `usr/bin/login.c` — перебор паролей без throttling (в связке с пустым root-паролем из V2-CRIT-04 не имеет значения, но при починке модели привилегий станет актуальным).

## V2-LOW-05 — `curl(1)`: сумма возвратов snprintf без clamp → потенциальный stack overflow

`usr/bin/curl.c` (формирование `req_buf`): `req_len += snprintf(...)`; при усечении (`-H`/`-d` длиннее буфера) `req_len` превышает `sizeof(req_buf)`, дальше `req_buf + req_len` и `sizeof(req_buf) - req_len` (underflow) → запись за пределами стека. Триггер — данные атакующего в аргументах (скрипты, передающие curl непроверенные строки). Фикс: `snprintf` с остатком буфера и `if (req_len >= sizeof(req_buf)) break;`.

## V2-LOW-06 — TSC-частота по умолчанию захардкожена (2.4 ГГц)

`idt.c:17` — при сбое калибровки PIT2 все тайминги (`timer_get_uptime_*`) врут на порядок; влияет на таймауты безопасности, если появятся.

# Системные выводы второго прохода

1. **Дисциплина блокировок отсутствует как класс.** Каждая подсистема изобретает свой протокол: pipe отпускает лок вокруг копирования, COW-фолт не берёт лок вообще, пулы потоков ищутся без лока, счётчики реестра инкрементируются мимо лока. На SMP почти любой системный вызов — потенциальная гонка. Рекомендуется ввести общий код-ревью-чеклист: «мутация разделяемого состояния → только под локом, копирование пользовательских данных → только вне лока, через copyin/copyout».
2. **Копирование из userland — непоследовательно.** Где-то `copyin`, где-то прямое разыменование (`serial_puts`, дамп стека в #PF, `strlen` по argv в загрузчике). Прямое разыменование пользовательского указателя = паника ядра. Нужен единый макрос `CHIMERA_USER_ACCESS(...)`.
3. **Модель привилегий отсутствует целиком**: `setuid`/`kill`/`/dev/disk0`/`/dev/mouse`/ptmx/open — всё доступно всем. Пустой root-пароль делает `login`/`su` декорацией. Это главный архитектурный долг после багов тома 1.
4. **Ресурсные лимиты отсутствуют**: стек по требованию без RLIMIT, пулы 64/64/32/512 с паникой или тихим отказом, непрерываемые ожидания. Fork-бомба из shell-скрипта укладывает систему тремя разными способами (паника очереди, утечка слотов, неубиваемые ожидания).
